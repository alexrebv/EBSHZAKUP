# Пересчёт по размерам

Сервис тянет остатки и заказы пяти маркетплейсов в Google Таблицу.
Расписанием управляет сама книга: лист «Настройки», блок задач со строки 15.

## Что куда пишется

Двадцать листов, по четыре на площадку: остатки FBO, остатки FBS, заказы FBO,
заказы FBS. Листы остатков перезаписываются целиком — остаток это снимок,
история в нём не нужна. Листы заказов дозаписываются: строка с тем же ключом
обновляется, новая уходит в конец.

Правее колонок схемы на листах лежат служебные колонки книги — ключи окна,
недели и месяца. Их считают формулы, сервис до них не дотягивается.

## Запуск локально

```bash
npm install
cp .env.example .env     # заполнить ключи
npm run once             # один проход по включённым задачам
node src/index.js --task "FBO остатки ВБ"   # одна задача принудительно
npm test                 # проба обхода отправлений Ozon, сеть и ключи не нужны
```

## Railway

1. Залить репозиторий на GitHub.
2. В Railway создать проект из этого репозитория.
3. В Variables задать переменные из `.env.example`.
4. Сервис поднимется сам: `railway.json` уже задаёт команду запуска.

Публичный порт не нужен — это воркер, а не веб-сервис.

## Переменные окружения

| Переменная | Зачем |
|---|---|
| `SHEET_ID` | идентификатор таблицы из её адреса |
| `GOOGLE_SERVICE_ACCOUNT_JSON` | ключ сервисного аккаунта, сырой JSON или base64 |
| `WB_STATS_KEY` | токен статистики WB: заказы и продажи FBO |
| `WB_ANALYTICS_KEY` | токен категории «Аналитика»: остатки FBO. Пусто — берётся `WB_STATS_KEY` |
| `WB_MARKET_KEY` | токен маркетплейса WB: остатки и задания FBS |
| `OZON_CLIENT_ID`, `OZON_API_KEY` | доступ Ozon, один на обе схемы |
| `YM_API_KEY` | ключ Яндекс Маркета |
| `YM_CAMPAIGN_FBS`, `YM_CAMPAIGN_FBY` | **разные** номера кампаний |
| `LAMODA_TOKEN` | Seller Partner API, JSON-RPC: товары и остатки |
| `LAMODA_B2B_TOKEN` | B2B Platform API, REST: заказы |
| `TZ` | часовой пояс сервиса, по умолчанию `Europe/Moscow` |

Сервисному аккаунту нужно выдать доступ к книге на редактирование —
его почта лежит в поле `client_email` внутри ключа.

## Что стоит знать

**Wildberries.** Статистика живёт на отдельном хосте с лимитом один запрос
в минуту на аккаунт, а не на метод. Паузу сервис выдерживает сам: перед каждым
обращением к статистике ждёт, пока с прошлого пройдёт минута. Поэтому задача
«Заказы ВБ FBO» честно занимает около двух минут — заказы и продажи это два
запроса.

Остатки FBO берутся методом аналитики `/api/analytics/v1/stocks-report/wb-warehouses`:
`/api/v1/supplier/stocks` из статистики отключён и отвечает 404. Токен нужен
с категорией «Аналитика» (`WB_ANALYTICS_KEY`), лимит — 3 запроса в минуту
с интервалом 20 секунд, данные на стороне WB обновляются раз в полчаса.

**Разбивки по складам у этого метода нет.** WB отдаёт единственный псевдосклад
`Склад WB` с `warehouseId: -999999`, поэтому колонка «Склад» одинаковая у всех
строк. Имя берётся из ответа, так что если WB вернёт настоящие склады, они
приедут сами. Строка ответа — это один размер товара, «в пути» приходит в той
же строке, отдельной строки «В пути» больше нет.

Штрихкода и артикула продавца в ответе тоже нет — только `nmId` и ID размера.
Первые две колонки листа собираются из справочника карточек. Из-за этого
остаткам FBO, как и остаткам FBS, нужен обход `content/v2/get/cards/list`;
обе задачи идут в одном проходе подряд, поэтому справочник кэшируется на пять
минут и обходится один раз. Если размера нет в карточках, штрихкод останется
пустым, а число таких строк будет указано в колонке «Результат».

Признака выкупа в заказах нет, поэтому он сверяется с отчётом `supplier/sales`
по идентификатору `srid`.

**Ozon.** У FBO и FBS разные методы и разные наборы статусов: по FBO они
приходят на английском (`delivered`, `cancelled`), по FBS на русском.
Формулы книги учитывают оба варианта.

Списки отправлений отдают не больше сотни за раз, в отличие от остальных методов
Ozon с их тысячей: на `limit: 1000` приходит 400 «value must be inside range
(0, 100]». А листаются они курсором — `cursor` приходит в ответе и уходит в
следующий запрос. Ни `offset`, ни `dir` в схемах `/v3/posting/fbo/list` и
`/v4/posting/fbs/list` нет вовсе: сортировку эти методы берут из `sort_dir`.

Именно на этом сервис и стоял. Он слал `offset` и `dir` — поля прежних поколений
методов, `/v2/posting/fbo/list` и `/v3/posting/fbs/list`, отключённых 31 августа
2026 года. Лишние поля метод молча выбрасывает, а пустой курсор значит «с начала
выборки», поэтому на любой странице приходила одна и та же первая сотня. Прогон
упирался в предел страниц и заканчивался ошибкой «ПАГИНАЦИЯ НЕ ЛИСТАЕТ» — причём
и тогда, когда все заказы на самом деле были прочитаны.

Теперь запрос держится схемы, а обход не полагается на один механизм: сломала его
как раз смена поколения метода. Механизмов три, и каждый следующий включается сам,
когда предыдущий перестаёт двигать выборку:

1. **курсор метода** — родная пагинация; имя поля берётся из ответа, поэтому
   `last_id` у других методов Ozon подхватится так же;
2. **дата** — страница отсортирована по возрастанию, значит её последняя дата и
   есть граница прочитанного: `filter.since` сдвигается на неё. Поле выбирается
   по самой странице: годится только то, по которому она не убывает и вся лежит
   не раньше начала окна, — иначе метод сортирует по одному полю, а сдвиг шёл бы
   по другому. У FBO это обычно `created_at`, у FBS такого поля нет вовсе, там
   `in_process_at`;
3. **делёж окна** пополам — `since` и `to` метод соблюдает (у FBS они обязательны),
   поэтому половина окна это заведомо другая выборка.

Дочитанность признаётся по слову метода — `has_next: false`. Недолитая страница
концом не считается, а ответ вовсе без списка отправлений (пустое тело, 204,
чужая форма) — тем более: и то и другое обрезало бы выборку молча. Границу
прочитанного двигает только первая страница окна, повторы на стыках снимает
указатель номеров отправлений, а швы окон нарочно перекрываются на миллисекунду —
если метод понимает `since` или `to` строго, отправление на границе не выпадет.

Период длиннее года метод не берёт, поэтому первичная заливка сразу режется на
окна по 180 дней. Чем листалось, видно в колонке «Результат»: «листали: курсор»,
«листали: дата», «листали: дата + делёж».

Окно, которое уже не делится, а сотня отправлений в нём не кончается, — честная
недочитка: прогон падает, водяной знак не сдвигается, и следующий заход попробует
снова.

Обход вынесен под пробу: `npm test` гоняет его против поддельного метода, который
держит схему строго и отвечает 400 на любое поле не из неё. Ключей и сети для
этого не нужно — на живом API повадки пагинации не проверить.

**Яндекс.** FBY и FBS — разные кампании с разными номерами. При чужом номере
метод вернёт пустой список без ошибки. Даты приходят как `ДД-ММ-ГГГГ`,
конструктор `Date` такое читает неверно, поэтому разбор ручной.

Метод заказов не принимает интервал длиннее 30 суток — на 33 днях отвечает
`400 Invalid filters: interval between dates`. Поэтому период режется на окна
по 28 дней и проходится подряд. Отдельно стоит знать: заказы, доставленные или
отменённые больше 30 дней назад, этот метод не отдаёт вовсе, так что глубже
месяца история отсюда не берётся ни при какой глубине.

**Ламода.** Два интерфейса одновременно: JSON-RPC для остатков и REST для
заказов, с разными токенами. Если дадут доступ к новому Seller Partner v2,
оба можно будет свести к одному REST.

**М.Видео.** Публичного API для продавцов нет. Четыре листа под них в книге
есть, заполняются выгрузкой из кабинета вручную. Задачи по ним выключены.

## Даты в книге

Сервис читает книгу с `UNFORMATTED_VALUE`, поэтому дата в ячейке приходит не
строкой, а числом — днями от 30.12.1899. «15.08.2026» на листе доезжает как
`46249`. Такое число нельзя отдавать конструктору `Date`: он посчитает его
миллисекундами. Разбирает ячейки только `изТаблицы` из `src/http.js` — и для
колонки «С даты», и для «Последний запуск». Обе колонки можно заполнять как
датой, так и текстом `ДД.ММ.ГГГГ`.

## Период выгрузки заказов

Три поля работают вместе, а не вместо друг друга.

| Поле | Роль |
|---|---|
| «Глубина дней» | скользящее окно, которое обновляется каждый прогон |
| «С даты» | граница истории: раньше неё сервис не ходит никогда |
| «Последний запуск» | водяной знак: пока пуст, идёт первичная заливка с «С даты» |

Порядок такой. Первый прогон заливает всё с «С даты». Каждый следующий берёт
окно в «Глубина дней» назад: обновляет то, что в нём изменилось, и дозаписывает
новые заказы. Строки за пределами окна не трогаются — сузить глубину безопасно,
накопленная история никуда не денется.

Чтобы залить историю заново, очистите «Последний запуск»: пустая ячейка снова
означает первичную заливку. Менять «С даты» для этого недостаточно.

**Глубину надо выставить самому.** Пока в ней стоит 31 при «С даты» месячной
давности, окно так и остаётся месячным, и прогон легче не станет: правка даёт
возможность сузить окно, а не сужает его за вас. Разумные значения — 1–3 дня
для ВБ и столько, сколько живёт заказ до вручения, для остальных площадок
(см. ниже про то, по какой дате фильтрует каждый).

Если сервис простоял дольше глубины, окно растягивается назад до последнего
**успешного** прогона. Успех определяется по колонке «Результат»: запись,
начинающаяся с «ОШИБКА», водяной знак не двигает. Иначе один упавший прогон
навсегда оставил бы в книге дыру за свой период.

Чтобы метка успеха пережила ошибку, она дописывается в конец текста ошибки:
`ОШИБКА: ... | успех: 17.09.2026 09:43:04`. Стирать этот хвост руками не нужно —
по нему следующий прогон понимает, откуда продолжать.

## По какой дате фильтрует каждая площадка

Это решает, насколько узкой может быть глубина.

| Коннектор | Фильтр периода | Чем это грозит при узком окне |
|---|---|---|
| Заказы ВБ FBO | по дате **изменения** записи (`flag=0`) | ничем: смена статуса у старого заказа сама попадёт в окно |
| Заказы ВБ FBS | по дате создания задания | статус старого задания перестанет обновляться |
| Заказы ОЗОН FBO/FBS | по дате создания отправления | то же самое |
| Заказы Яндекс | по дате заказа | то же, плюс метод не отдаёт заказы старше 30 дней |

Иными словами: у ВБ FBO глубину можно ставить хоть в сутки — статусы всё равно
подтянутся. У остальных глубина должна покрывать цикл доставки, иначе заказ
навсегда останется в книге с тем статусом, в котором выпал из окна.

Семантика ВБ FBO проверена по документации. Остальные строки таблицы —
поведение внешних API, на боевых ключах не проверялось: если увидите, что
статусы застывают, увеличьте глубину.

В колонке «Результат» видно, какое окно взято на самом деле:
`период 10.09.2026 — 17.09.2026` или `первичная заливка с 18.08.2026`.

## Что означает «новых» и «изменено»

`новых` — заказов, которых в книге не было. `изменено` — строк, у которых
поменялись данные: статус, цена, склад. Если оба нуля, лист не переписывался
вообще: ни одного запроса на запись в Таблицы не ушло.

Неполный прогон успешным не считается. Если пагинация оборвалась, задача
падает с ошибкой, а не пишет «строк 100» как достижение: иначе водяной знак
уехал бы вперёд и недочитанное не вернулось бы уже никогда.

Листы остатков — снимки, они перезаписываются целиком. Пустой ответ от
маркетплейса снимок не стирает: задача падает с ошибкой, а прежние остатки
остаются в книге.

Из этого следует, что колонка «Обновлено» показывает, когда строка в последний
раз **менялась**, а не когда сервис на неё последний раз смотрел. Когда сервис
смотрел — написано в «Последний запуск» на листе настроек.

## Объём листов

Листы заказов сервис читает до 50000-й строки — по ним строится указатель
ключей. При приближении к пределу предупреждение уходит не только в журнал,
но и в колонку «Результат». Если предел всё-таки достигнут, задача падает
с ошибкой и ничего не пишет: строки за пределом невидимы для указателя,
дозапись легла бы поверх них. Историю пора уносить в архивный лист.
