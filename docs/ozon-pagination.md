# Ozon: «ПАГИНАЦИЯ НЕ ЛИСТАЕТ» — что делать

```
[/v3/posting/fbo/list] ПАГИНАЦИЯ НЕ ЛИСТАЕТ: метод повторяет первые 100 отправлений
[fail] Заказы ОЗОН FBO: строк 100, новых 9, изменено 2, ПАГИНАЦИЯ НЕ ЛИСТАЕТ: ...
[/v4/posting/fbs/list] ПАГИНАЦИЯ НЕ ЛИСТАЕТ: метод повторяет первые 100 отправлений
[fail] Заказы ОЗОН FBS: строк 100, новых 7, изменено 3, ПАГИНАЦИЯ НЕ ЛИСТАЕТ: ...
```

## Короткий ответ

**Править код не нужно — он уже исправлен и лежит в `main`.** Это сообщение
печатает старая версия сервиса. Нужно передеплоить и перечитать историю.

| | |
|---|---|
| `main` | `165beb6` |
| Что вошло | `9b548d5`, `1754514`, `165beb6` |

## Как убедиться, что дело именно в деплое

Строки «ПАГИНАЦИЯ НЕ ЛИСТАЕТ» в исправленном коде **нет вообще**:

```bash
git -C . grep -n "ПАГИНАЦИЯ" -- src/
# ничего не находит
```

Она осталась только в `README.md` (как описание прошлого) и в комментарии пробы.
Раз сообщение всё ещё приходит — работает не тот код.

**Самый быстрый признак, не заходя в git.** У новой версии в колонке
«Результат» всегда есть хвост `, отправлений N, запросов M, листали: …`.
В старой версии таких слов не было вовсе.

> Нет слова **«листали:»** в «Результате» — значит крутится старый код.

## Что было на самом деле

Сервис слал методам `offset` и `dir`. У `/v3/posting/fbo/list` и
`/v4/posting/fbs/list` **таких полей нет** — по схеме Ozon их ровно шесть:
`cursor`, `filter`, `limit`, `sort_dir`, `translit`, `with`. Листаются эти методы
курсором, сортировка задаётся через `sort_dir`.

`offset` и `dir` остались от прежнего поколения методов
(`/v2/posting/fbo/list`, `/v3/posting/fbs/list`), **отключённого 31 августа
2026 года**. Неизвестные поля метод молча выбрасывает, а пустой курсор значит
«с начала выборки» — поэтому на любой странице приходила одна и та же первая
сотня. Пути в коде были уже новые, отстала только пагинация.

Теперь запрос держится схемы, а листается обход тремя механизмами, каждый
следующий включается сам, когда предыдущий перестаёт двигать выборку: **курсор
метода** → **рез окна по дате страницы** → **делёж окна пополам**.

## Порядок действий

### 1. Передеплоить сервис

Railway, `railway.json` уже задаёт команду запуска — трогать его не нужно.

1. Открыть проект в Railway → сервис → **Settings → Source**.
2. Убедиться, что сервис подключён к ветке **`main`** этого репозитория.
   Если подключён к другой ветке — переключить на `main`.
3. **Deployments** → убедиться, что последний деплой собран из `165beb6`
   или новее. Если автодеплой выключен или не сработал — **Redeploy**.

Сборка ставит зависимости заново (`package-lock.json` в репозитории нет,
это как и было). Добавленный скрипт `npm test` на деплой не влияет: Nixpacks
запускает `startCommand` из `railway.json`, а `build`-скрипта в проекте нет.

### 2. Дождаться прогона и посмотреть «Результат»

Задачи Ozon ходят по расписанию из книги («Настройки», колонка «Каждые»).
Можно дождаться, можно прогнать принудительно:

```bash
node src/index.js --task "Заказы ОЗОН FBO"
node src/index.js --task "Заказы ОЗОН FBS"
```

Здоровая строка выглядит так:

```
строк 1240, новых 83, изменено 12, отправлений 1240, запросов 13,
листали: курсор, 6.1 c, период 08.09.2026 — 22.09.2026
```

Главное в ней — **`листали: курсор`** и **`строк` заметно больше сотни**.

### 3. Добрать пропущенное

Починка возвращает будущее, но не прошлое: заказы, лежавшие за первой сотней
в пропущенные дни, в книгу не попали и сами не появятся.

Для обеих задач — «Заказы ОЗОН FBO» и «Заказы ОЗОН FBS»:

1. В **«С даты»** поставить дату, с которой нужна история.
2. **Очистить «Последний запуск»** — пустая ячейка означает первичную заливку
   с «С даты».
3. Дождаться прогона.

Уже записанные заказы обновятся по ключу («Отправление» + «SKU»), пропущенные
допишутся. Задваивания не будет.

Заливка идёт заметно дольше обычного прогона. Период глубже года сервис сам
режет на окна по 180 дней — метод длиннее не берёт.

### 4. Убедиться, что починилось

* Слова «ПАГИНАЦИЯ НЕ ЛИСТАЕТ» в логе нет ни при каком исходе.
* В «Результате» есть `листали:` — работает новый код.
* `строк` больше 100 и перестало быть подозрительно круглым.
* «Последний запуск» обновляется, а период в «Результате» больше не
  расползается назад день за днём.

## Словарь сообщений новой версии

### Прогон успешен

| В «Результате» | Что значит | Что делать |
|---|---|---|
| `листали: курсор` | Метод листается своей родной пагинацией. Норма. | Ничего |
| `листали: дата` | Курсор метод не отдал или отдал впустую, обход пошёл резом окна по дате. **Данные полные.** | Ничего. Если появилось внезапно — Ozon опять сменил схему, стоит заглянуть в неё |
| `листали: дата + делёж` | Не сработали и курсор, и рез по дате; окно доедено делением пополам. Данные полные, запросов больше. | Ничего |
| `без ключа пропущено N` | N строк пришли без номера отправления и в лист не записаны. | Разово — можно не обращать внимания. Постоянно — смотреть ответ метода |
| `строк N при пределе 50000 — пора в архив` | Лист подходит к пределу чтения. | Перенести старые заказы в архивный лист |

### Прогон упал (и это правильно)

Любая из этих строк означает: прочитано не всё, поэтому отметка успеха **не**
сдвинута и следующий заход попробует снова. Глушить их нельзя — иначе
недочитанное не вернётся никогда.

| В «Результате» | Что значит | Что делать |
|---|---|---|
| `окно на ДД.ММ.ГГГГ ЧЧ:ММ:СС уже не делится, а 100 отправлений в нём не кончаются` | Больше сотни отправлений в одном мгновении, а курсор не работает. Крайне редкий случай. | Проверить, отдаёт ли метод `cursor`: если отдаёт, а обход его не берёт — смотреть ответ |
| `метод ответил без списка отправлений на окне с ДД.ММ.ГГГГ ЧЧ:ММ:СС` | Пустое тело с кодом 200, 204 или ответ чужой формы. Раньше такое молча считалось концом окна. | Обычно разовый сбой, проходит сам. Повторяется — смотреть, что отдаёт Ozon |
| `прочитано N отправлений и упёрлись в предел 500 запросов — сузьте период` | В окне больше ~50 000 отправлений. | Уменьшить «Глубина дней» или поднять «С даты» |

В логе контейнера рядом может встретиться `курсор не двигает выборку, дальше
идём по дате` — это не ошибка, а отметка о том, что обход переключился на
страховку. Прогон при этом успешен.

## Если передеплоить прямо сейчас нельзя

Временная мера, **из книги, без правки кода**. Она не чинит пагинацию, а лишь
останавливает разрастание окна.

Окно считается как «сейчас минус Глубина дней», но растягивается назад до
последнего **успешного** прогона. Прогон с ошибкой успешным не считается,
поэтому окно расширяется каждый день, отправлений в него попадает всё больше,
и защита срабатывает всё вернее. Само это не рассосётся.

«С даты» обрезает окно снизу и перебивает растяжение:

1. У задач «Заказы ОЗОН FBO» и «Заказы ОЗОН FBS» поставить в «С даты»
   вчерашнюю или сегодняшнюю дату.
2. Посмотреть «Результат»: если `строк` меньше 100 и ошибки нет — окно
   уложилось в предел, рост остановлен.
3. Если ошибка осталась — значит и за сутки больше сотни отправлений, и мера
   не поможет. Тогда только деплой.

**Пропущенное это не возвращает.** После деплоя всё равно нужен пункт 3
основного порядка.

## Чего делать не нужно

* **Не глушить предупреждение.** Без него неполный прогон считается успешным,
  отметка успеха сдвигается, и недочитанные заказы не вернутся уже никогда —
  это и был исходный дефект.
* **Не поднимать `limit` выше 100.** По схеме `maximum: 100`, на 1000 метод
  отвечает `400 value must be inside range (0, 100]`.
* **Не увеличивать предел запросов.** Если выборка не двигается, лишние
  страницы дадут только повторы.
* **Не возвращать `offset` и `dir` в запрос.** Их у этих методов нет; метод их
  молча выбрасывает, и запрос снова начнёт выглядеть рабочим, не будучи им.
  Проба это ловит: поддельный метод отвечает 400 на любое поле не из схемы.
* **Не откатываться на `/v2/posting/fbo/list` и `/v3/posting/fbs/list`.**
  Они отключены 31 августа 2026 года.

## Приложение: для того, кто будет править код дальше

| Что | Где |
|---|---|
| Обход отправлений | `src/wb-ozon.js`, `ozonОтправления` |
| Поля схем: метод, лист, поле даты | `src/wb-ozon.js`, `ОТПРАВЛЕНИЯ` |
| Превращение недочитки в ошибку | `src/wb-ozon.js`, `ozonЗаказы` |
| Период и водяной знак | `src/http.js`, `период` |
| Проба | `проба/отправления-ozon.test.js`, `npm test` |

Проба гоняет обход против поддельного метода, который держит схему строго и
отвечает 400 на любое поле не из неё. Ключей и сети не нужно: на живом API
повадки пагинации не проверить, а меняются они, как видно, вместе с поколением
метода.

**Два места, где легко сделать хуже, если не знать.**

*Первое.* Соблазнительно двигать `filter.since` на дату последней строки
страницы. Так обход молча полагается на то, что метод сортирует ровно по тому
полю, по которому считает период, — а в схеме про поле периода не сказано
ничего. Если поля разойдутся, начало окна перескочит через хвост сортировки, и
отправления пропадут без единого слова: на симуляции это давало 208 из 250 при
пустом `недочитано` и успешном прогоне. Поэтому дата **режет конец** окна, а
начало не двигает никогда: две половины покрывают окно целиком при любом месте
реза, потому что рез идёт по той же числовой прямой, по которой метод
фильтрует.

*Второе.* Правая половина при резе начинается **миллисекундой раньше** места
реза. Понимание границ у метода неизвестно, и пойми он строго и `since`, и
`to` — отправление ровно на шве выпало бы из обеих половин. Перекрытие снимет
указатель прочитанных номеров, а вот потерю на шве не заметил бы никто: на
группе отправлений с одной датой это давало 246 из 250.

Обе ошибки были сделаны и пойманы при работе над этой правкой; в пробе на них
стоят отдельные случаи.
