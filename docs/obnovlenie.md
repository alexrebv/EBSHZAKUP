# Как обновлять код

Порядок работы над этим сервисом: что править под каждую типовую задачу, чего
не делать никогда и как убедиться, что стало лучше, а не хуже.

Устройство — в [`roadmap.md`](roadmap.md), все зашитые значения — в
[`reestr-kodov.md`](reestr-kodov.md).

---

## 0. Главное правило

**Молчаливая потеря данных хуже честного падения.**

Из него следует почти всё остальное. Пустой ответ, который можно спутать с
«данных нет», должен становиться ошибкой. Курсор, который не двигает выборку, —
ошибкой. Ноль строк в снимке — ошибкой. Задача, упавшая с внятным текстом в
колонке «Результат», чинится за пять минут. Задача, которая год писала половину
заказов и отмечалась успешной, не чинится вообще: данных за этот год уже нет.

---

## 1. Прежде чем начать

```bash
git checkout -b claude/что-делаем          # ветка под задачу
npm install
npm test                                   # должно быть зелено ДО правок
```

Если пробы красные до ваших правок — сначала разберитесь с этим. Иначе в конце
вы не отличите свою поломку от чужой.

Сеть для проб не нужна: маркетплейсы поднимаются поддельными серверами на
localhost, книга подменяется через `подставитьКлиент()`.

---

## 2. Правило про пробы

> Починка принимается только вместе с пробой, про которую **доказано**, что на
> прежнем коде она падает.

Проба, которая проходит и на старом коде, ничего не проверяет. Проверять это
надо руками, а не на глаз:

```bash
git stash                 # убрать починку, оставить пробу
npm test                  # проба ОБЯЗАНА упасть
git stash pop             # вернуть починку
npm test                  # проба обязана пройти
```

В этой работе один раз попалась проба, которая проходила и до, и после: она
брала 300 строк, а порог, который проверялся, срабатывал с 200 диапазонов —
и до него просто не доходило. Пробу переписали на 500 строк, и она начала
ловить.

## 3. Типовые задачи

### 3.1. Добавить колонку в существующий лист

1. `src/schemas.js` → `СХЕМЫ['Имя листа']` — добавить заголовок **в конец, но
   перед `'Обновлено'`**. «Обновлено» обязана остаться последней: сравнение
   строк пропускает именно последнюю колонку.
2. Коннектор — добавить значение в том же месте массива строки.
3. Проверить `КЛЮЧИ` для этого листа: если индексы колонок сдвинулись, поправить.
4. В книге колонку **не двигать руками** — сервис допишет заголовок сам в пустую
   клетку. Если клетка занята, он её не тронет.

Осторожно: правее колонок схемы на листах лежат служебные колонки книги с
формулами. Расширяя схему, вы наезжаете на них. Сначала посмотрите в книгу.

### 3.2. Добавить новый лист или задачу

1. `src/schemas.js`:
   * `СХЕМЫ['Новый лист'] = [...]` — колонки, `'Обновлено'` последней;
   * `КЛЮЧИ['Новый лист'] = [...]` — если лист дозаписывается, а не снимок;
   * если имя задачи в книге **не совпадает** с именем листа — добавить его в
     `ЗАДАЧИ` (как сделано для `Возвраты OZON FBS`).
2. Написать коннектор: функция принимает `задача`, возвращает строку-отчёт для
   колонки «Результат».
3. `src/index.js` → `ОБРАБОТЧИКИ['Имя задачи'] = коннектор`.
4. В книге: завести лист и строку в блоке задач (строки 15–60).
5. Пробу — на сборку строки и на пагинацию.

Лист, в имени которого есть слово «остатки», автоматически считается снимком и
перезаписывается целиком. Это удобно, но помните про это, называя лист.

### 3.3. Подключить новый метод API

Поднимите проверку ответа сразу, а не потом:

```js
const тело = ответ.result || ответ;
if (!Array.isArray(тело.items)) {
  throw new Error(`метод ответил без списка на странице ${n + 1}`);
}
```

Метод, который на ошибку отвечает `200` с пустым телом, — не редкость. Без этой
проверки прогон запишется успешным, а лист останется пустым.

Дальше по порядку:

* **Пагинация.** Не верьте `offset`, пока не проверили. Ozon его молча
  выбрасывает: запрос отвечает `200` и на любой странице отдаёт одну и ту же
  первую сотню. Признак — число строк, кратное размеру страницы и ровно равное
  ему. Разбор случая — в [`ozon-pagination.md`](ozon-pagination.md).
* **Предел страницы.** Пробуйте с предельным значением из документации, а не
  «покрупнее». Ozon на `limit: 1000` отвечает `400`.
* **Курсор.** Всегда сверяйте новый курсор со старым: равный курсор — это
  бесконечный круг, и он должен падать, а не крутиться.
* **Лимит запросов.** Если метод лимитирован, держите паузу сами через
  `неЧаще(ключ, мс)`. Лимиты у маркетплейсов обычно на аккаунт, а не на метод.
* **Текстовые значения.** Артикул, штрихкод, размер, название — всё через
  `текстом()`. Числа, по которым книга считает формулами (SKU, цена,
  количество), — **без** него.

### 3.4. Поменять период или расписание

**Через код — почти никогда.** Частота, глубина и «С даты» живут в книге, на
листе «Настройки». Это сделано нарочно: менять их должен тот, кто смотрит в
таблицу, а не тот, кто умеет деплоить.

Код трогают, только когда меняется сама **логика** периода — тогда это
`период()` в `src/http.js` и проба в `проба/настройки.test.js`.

Частый вопрос «почему история не загрузилась»: правки «С даты» мало, нужно ещё
очистить «Последний запуск». Сервис сам пишет об этом в «Результат».

### 3.5. Поменять лимит или предел

Все они собраны в [`reestr-kodov.md`, раздел 5](reestr-kodov.md#5-числовые-пределы).
Правя значение в коде, поправьте и реестр — иначе он начнёт врать, а врущая
документация хуже отсутствующей.

### 3.6. Разобраться, почему задача падает

1. Колонка «Результат» на листе «Настройки» — там текст ошибки целиком, до 400
   символов.
2. Журнал Railway — там же `[fail] Имя задачи: …`.
3. Прогнать одну задачу вручную:
   ```bash
   node src/index.js --task "Заказы ОЗОН FBO"
   ```
   Это идёт мимо расписания и пишет результат в книгу, как обычный прогон.

Если в «Результате» стоит `ОШИБКА`, а рядом `| успех: …` — метка последнего
успеха цела, период не уехал, потери данных нет.

## 4. Чего не делать

| Нельзя | Почему |
|---|---|
| Сдвигать строки на листе «Настройки» | Сервис читает их по номерам: `A3:B12`, `A15:G60`. |
| Переименовывать листы в книге, не правя `СХЕМЫ` | Имена сверяются посимвольно, включая пробелы. |
| Писать в книгу прочитанное из книги | Апостроф-пометка «текст» обратно не приходит — артикул снова разберётся как дату, формула затрётся своим же значением. |
| Ставить «Обновлено» не последней | Сравнение строк пропускает последнюю колонку. Сдвинете — каждый прогон будет переписывать весь лист. |
| Заворачивать в `текстом()` числовые колонки | Формулы книги перестанут по ним считать. |
| Считать пустой ответ за «данных нет» | Это и есть тихая потеря данных. |
| Гонять задачи параллельно | Лимиты маркетплейсов на аккаунт; получите 429 на всём. |
| Повышать `ПРЕДЕЛ` вместо архивирования | 50 000 строк — это уже граница, за которой чтение листа само становится проблемой. |

## 5. Перед тем как отправлять

```bash
npm test                                   # все пробы
node src/index.js --task "Имя задачи"      # если есть доступ к тестовой книге
git diff                                   # перечитать свой диск глазами ревьюера
```

Вопросы к себе по диффу:

* Может ли эта правка молча вернуть меньше данных, чем раньше?
* Что будет, если метод ответит `200` с пустым телом?
* Что будет, если в ячейке книги окажется мусор вместо даты?
* Если правка про запись в книгу — не уходит ли в неё что-то прочитанное **из**
  книги?

Коммит — одной мыслью, заголовком по-русски, в повелительном наклонении:

```
Починить пагинацию возвратов: last_id вместо offset
```

## 6. Как поддерживать эти документы

Три файла, и у каждого своя зона:

| Файл | Обновлять, когда |
|---|---|
| `roadmap.md` | поменялась структура: модули, порядок прохода, режимы записи |
| `reestr-kodov.md` | поменялось любое зашитое значение: адрес, метод, лимит, имя листа, номер строки |
| `obnovlenie.md` | появилась новая типовая задача или новый способ выстрелить себе в ногу |

`reestr-kodov.md` ссылается на код номерами строк. Они устаревают. Проверить
все ссылки разом:

```bash
npm run проверить-ссылки
```

Команда проходит по всем `файл.js:номер` в документации и ругается на те, что
указывают за пределы файла или в пустую строку. Содержимое она не сверяет —
это всё ещё на вас.

Полный свод исходников (все файлы одним документом) собирается командой:

```bash
npm run свод
```

Он кладётся в `docs/ves-kod.md`. Это **снимок**, а не источник правды: правьте
`src/`, а свод пересобирайте. Устаревший свод хуже, чем никакого, поэтому
пересобирайте его в том же коммите, где меняли код, — или не храните вовсе.
